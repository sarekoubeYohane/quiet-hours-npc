# 完整回合的有界時間政策（#166／#168）

規格：[#166](https://github.com/sarekoubeYohane/quiet-hours-npc/issues/166)，唯一工作票 [#168](https://github.com/sarekoubeYohane/quiet-hours-npc/issues/168)。本文件是工程契約；[原診斷](../verification/round-deadline-diagnosis-2026-10-25.md)保留修正前證據，[Grill](round-deadline-grill-2026-10-25.md)記錄較長但有限等待的取捨。數值不屬於領域詞彙，不加入 GLOSSARY。

## 容量推導

N 是當輪角色集合大小，R 是當輪合法回想續答數，0 ≤ R ≤ N。聊天上限 C ≤ 2N + R ≤ 3N；一個 slot 最多一次初次決策、一次回想續答、一次裁定，玩家原有預算可能更早停止。這項修正不增加呼叫、重試、角色或模型。

### 2026-11-26 起：串流與兩段等待

模型呼叫改用串流後，單次呼叫**沒有固定總時限**：

- **首段回應時限** `modelFirstByteMs` = 30 秒：送出後必須收到第一段資料；收到正文或思考內容之前，這個期限一直有效（只送 role 的空段不會讓之後的推理沉默改用較短的閒置時限）。保活訊號算有動靜。
- **閒置時限** `modelIdleMs` = 15 秒：相鄰兩段資料之間最多等這麼久。思考內容與保活訊號都算。
- 單次呼叫仍受該回合剩餘工作窗口限制（`modelSignal` 的期限就是 `workDeadline`）。準備、保存實錄與入帳不再被每次呼叫的 25 秒截斷，只受工作窗口限制。

25 秒總時限的實際失效方式（測試站存檔「石室的湯」，2026-11-26 的決策實錄，gpt-6.2-sol，非串流）：

| 量測 | 範圍 |
| --- | --- |
| 25 秒 signal 建立到 fetch 開始（prepared 實錄保存、帳號預留） | 4.8–6.2 秒 |
| fetch 到 HTTP 標頭（NPC 決策，29 次成功） | 9.6–18.0 秒 |
| 標頭到本文收完 | 0.4–2.0 秒 |
| 裁定（1 次成功） | 標頭 7.8 秒、本文 8.6 秒 |

四次逾時中有三次是**本文已收完**（例如輸入 24,603、輸出 934 tokens 的那次在 fetch 後 18.8 秒收完），之後保存用量、候選與入帳的實錄寫入把總時間推過 25 秒；只有一次（裁定）是 fetch 後 20.2 秒仍沒有標頭的真正供應商等待。

首段 30 秒的依據：非串流的完成時間是首段資料到達時間的上限，已觀測最大值 18.8 秒，30 秒約為 1.6 倍。OpenAI 推理模型在推理期間是否送出任何資料，官方文件沒有寫明；串流上線後以決策實錄的 `firstChunkAt`、`firstContentAt` 實測再調整。

### 容量表

單次呼叫已不是固定的 25 秒，下表以實測加上限推出每次聊天的規劃包絡：

| 成本 | 每次 | 依據 |
| --- | ---: | --- |
| 準備與送出前保存 | 6 秒 | 實測 4.8–6.2 秒 |
| 供應商：首段到達 | ≤ 30 秒 | 首段時限 |
| 供應商：正文串流 | 約 2 秒（NPC 約 900 tokens） | 實測標頭後 0.4–2.0 秒；串流後首段到結尾仍待實測 |
| 收到後保存與入帳 | 4 秒 | 實測超過 2.8 秒，取整留餘量 |
| **每次聊天規劃值** | **42 秒** | 首段打滿時；實測最慢一次約 28 秒 |

| 情境 | 推導 | 合計 | 對 400 秒工作窗口 |
| --- | --- | ---: | --- |
| 實測典型：四人、無裁定 | 4 × 28 + 外層 60 | 172 秒 | 足夠 |
| 四人各一次裁定 | 8 × 28 + 60 | 284 秒 | 足夠 |
| 四人、裁定、首段都打滿 | 8 × 42 + 60 | 396 秒 | 剛好在邊界 |
| 最壞：12 次聊天、4 次回想、首段都打滿 | 12 × 42 + 4 × 10 + 60 | 604 秒 | **超過** |

目前常數**維持不變**：工作窗口 400 秒、提交／回復餘量 30 秒、租約 430 秒、前端等待 445 秒（`roundTimePolicy.workMs`、`finishMs`、`deliveryMs`）。後果是最壞情境不再保證完成：回想與裁定都發生、而且每次都等到首段時限時，回合會在工作窗口用完時以「在本回合工作窗口用完時中止」回復，畫面寫明是哪一位人物的哪一項呼叫。是否把窗口放寬到約 610 秒（租約 640、前端 655）尚待確認，見下方待決事項。

這些上限是應用政策，並非 Cloudflare 固定執行時間。任意慢保存、無限大世界或服務失聯不在成功保證內。

## 順序、停止與不可取消工作

NPC 仍逐 slot 決策，承接先前候選的可知變化。故事、記憶、意圖及回饋在同一次世界 CAS 提交；提交前技術失敗回復整輪，保留已知用量與未知標示。正常 denied／unsupported 仍是角色可知回饋。沒有並行 NPC、部分提交、續租、heartbeat 或背景接續。

必要保存維持 await 與原序列 queue。截止只能停止等待，不能宣稱底層 SQL 或服務已取消；晚到工作只能完成原本的證據責任，不能重啟 parser、決策、擲骰或候選提交。租約、版本、原 pending 與 CAS 共同防止覆蓋較新世界。CAS 拋錯先查 durable journal；已提交世界不因最後 trace 故障回復。資料庫完全不可用時回報不明，不能承諾所有用量立即持久化。

## 相容與恢復

新前後端共用等待政策。舊分頁的 125 秒計時器無法由新版 server 延長，新付費advance必須送出 `X-World-Time-Policy: round-v1`，否則受理前回426／clientUpdateRequired要求更新；原有已受理 ID 的查詢與精確回放仍可使用，不要求新header。受理前setup／租約取得超過15秒則在首次付費前停止；HTTP總截止也傳入工作signal及實際CAS時間fence，不能讓較晚受理的工作在回應停止後繼續。15秒是受理前與交付的合計餘量，並非兩者各15秒。既有 pending 依資料庫原存的絕對期限解析，不能套新常數延長或縮短。

重載、斷線及回到前景先以原 ID 唯讀查證。pending／uncertain 保留 sessionStorage 與原 payload，停用新的 advance；自動運行不能重疊。唯讀查詢不派送，已定案同 ID POST 精確重放原 status／body，不重套效果或計費。

## 證據與隱私

時間證據沿既有私有決策實錄保存：租約／工作／signal 截止、prepared 與實際 fetch、headers／body、usage 已知、checkpoint 與提交／回復窗口。串流的回覆另記 `responseAssembledFromStream`、`firstChunkAt`（任何一段，含保活）、`firstContentAt`（第一段正文或思考）、`lastChunkAt`、`streamChunks`；`responseBody` 是由串流組成的完整回覆。缺失時間是未知，不能從差額猜 provider 或 D1 責任。沿用原 owner 權限、Key 遮蔽、1 MiB 單筆／64 筆／16 MiB 容量、淘汰、reset 與晚到 UPDATE 契約。

公開測試只使用合成資料；完整 transcript、記憶正文、世界備份及憑證不進公開 repo 或一般 logs。時間診斷不送進 NPC 輸入。lateUsage 是晚到證據，不重寫原定案費用或恢復執行。
