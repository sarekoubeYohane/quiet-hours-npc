## 已查證的實作落差

1. 實際候選同時提供 `routine.timings` 與數值 `completionMinutes`，重播經世界 API 與 SQLite 得到相同 502：「日常耗時須由整組規則確認。」通用提示要求核准完成目標填數值，日常解析卻要求 null；通用 accepted 必須有效果的提示也未明示日常核准的空效果例外。
2. 只將該候選 `completionMinutes` 改成 null，API 正常提交且保存六項規則，但 target=`acceptance-tea-kit` 時活動未完成、杯子仍空。再只將 target 改成 `acceptance-cup`，一個 15 分鐘單位後完成，重讀有茶。這些均為本機捕獲候選重播與明示 NPC 替身，並非新一輪正式模型驗收。
3. 現有 `bindRoutine` 已有從日常背景建立器具供應並具體化杯子的路徑；但提案指向具體茶具時，容器篩選限定同一 target，找不到杯子後又因 targetObject 存在直接否決，未進入該路徑。

本機診斷以正式報告捕獲的裁定作 transport fixture，透過實際世界 API 與 SQLite 保存／重讀；其餘 NPC 暫時接管以隔離變因。三組都只有一次 NPC 提案與一次裁定呼叫，沒有新增真實模型花費：

| 受控輸入 | API 與保存結果 | 活動結果 |
| --- | --- | --- |
| 原捕獲候選，`completionMinutes: 5`，指定茶具 | 502；turn 0、720 分鐘、無新規則 | 原子回復，杯子仍空 |
| 只將 `completionMinutes` 改為 null | 200；turn 1、735 分鐘、保存完整六項時間 | 活動未完成，杯子仍空；不是成功修復 |
| 再只將 target 改成現有杯子 | 200；turn 1、735 分鐘、保存完整六項時間 | 泡茶完成，SQLite 重讀杯子有茶 |

原始衝突候選仍應被拒絕；修正目標是讓模型收到一致的日常核准契約，並讓合法提案可承接正確物件，不能把上述測試輸入變更當作程式修正或正式站驗收。

## 已釐清方向

### Q1 修正：普通配備可以具體化

原提問將選擇限成「世界挑現有杯子」或「NPC 補選杯子」。使用者指出，天上意志應能生成一個可供 NPC 使用的杯子並標記。

承接為：世界主持可依已確認的日常供應背景，把普通杯子具體化成具有持續身份、可保存及追蹤狀態的世界物件，供 NPC 實際使用。這是 #108 已有的供應精細度方向，不要求玩家先逐只建好杯子；「標記」在本輪沿用既有具體物件的身份及狀態追蹤，未據此增加新 UI 或另定新權限。

工具與容器的角色承接整理於下方共同理解；物件暫不可用時的具體化邊界見 Q3。

### Q2：優先沿用可用的普通杯子（A）

使用者選擇 A：現場已有合法、乾淨、未被占用且符合這次活動要求的普通杯子時，優先沿用；需要另一只時，才從已確認的日常配備具體化。用過並洗好的杯子可回到後續日常使用，保留同一物件身份。NPC 的明確指定及既有使用權仍優先。

### Q3：已記錄杯子皆髒，但背景未確認耗盡（A）

使用者選擇 A：若已具體化的杯子都髒了，且咖啡館並未被設定為只有這幾只杯子、也未明確沒有乾淨杯子，允許從已確認的日常配備具體化另一只乾淨杯子。原髒杯保持同一身份與髒污，不被清潔、刪除或覆寫；不為了促成清洗行為強制 NPC 改做別的事。

若已明確沒有乾淨杯子，或 NPC 明確指定使用某只杯子，則不能以另一只杯子繞過該條件。已記錄物件的狀態與整體供應短缺須分開判斷，不由「所有已記錄杯子皆髒」直接推定整個咖啡館沒有其他杯子。

## 已確認的共同理解

1. 世界主持可依已確認的日常背景具體化所需普通配備，保存其身份及後續狀態；不要求玩家或 NPC 事前逐一列出所有配備。
2. 當下有合法、可知、可用且符合活動要求的普通杯子時優先沿用。需要另一只且沒有明確供應限制時，從背景具體化新杯子；舊物件及其後果保持。
3. 「使用這套茶具泡茶」約束所使用的工具，不等於「必須把茶裝進這套茶具物件」。世界承接該方法所需的杯子，沿前兩項處理。若角色明說「用這只杯子」，則保持指定杯子，不暗中代換。不能只靠固定物件 ID 特判修正驗收場景。
4. 普通方法的必要配備可由既有日常規則承接；需要改變角色明確方法、偏好、借用或他人同意的選擇，仍依 #108／既有控制與權限契約交回角色。受阻只回饋角色可知條件，不將未執行活動敘述成完成。
5. 時間與效果候選的提示、輸出格式及驗證須一致：日常核准以整組已確認時間作唯一來源，與一般效果裁定分開表達；保留無效候選拒絕及原子回復，不能靠放寬所有校驗修正。
6. 首次確認、適用規則免費重用、合理耗時、明確投入上限與階段效果沿 #108／#115。核准不代表已取得杯子或完成泡茶；時間不足未啟動時不提前具體化物件。單次 slot 派送上限與操作重送不重複執行保持。

## 修正 Issue 範圍

### 修正票一：統一日常核准與一般效果的時間／效果契約

- 修正已捕獲的實際模型輸入中的互相矛盾要求，令輸出格式與解析／執行分支一致。
- 保存完整整組時間確認及唯一時間來源，不透過固定泡茶時間、偷偷新增修復模型呼叫或忽略不合法候選掩蓋問題。
- 以捕獲候選重現原故障，補正確日常核准及一般效果分支的世界 API 回歸；驗證正常完成、非法候選回滾、已知用量與重送。

### 修正票二：承接工具提案與可持續追蹤的日常配備

- 同一自然提案能區分使用的工具與承裝成果的容器，按 Q1–Q3 沿用或具體化所需杯子。
- 覆蓋現有合法杯子、尚無具體杯子、已記錄杯子皆髒但背景未耗盡、明確無乾淨杯及明確指定杯子的不同情況。
- 保留身份、狀態、歸屬、使用權與活動階段；驗證重載、後續新活動重用及操作重送沒有多生杯子或覆寫髒杯。
- 真實世界 API／SQLite 為主要測試介面，沿既有真實應用瀏覽器操作確認可見結果及重載，不新增測試入口。正式站真實模型驗收與 fixture 明確區分。

兩票皆承接既有規格。建議先修正票一再完成修正票二的整合驗收；票二可先以合法日常候選獨立開發，兩票沒有硬性阻擋關係。原始正式站場景須兩票共同驗收通過，才能宣稱完整修復。
