# 通用世界變更框架：Grill 紀錄

狀態：Q1、Q2、Q4、Q5、Q6 已確認，Q3 原提問撤回；訪談進行中，不是完整規格、實作或正式站驗收結果。

使用者在釐清「由框架承接 LLM 確認的世界變化」後，明確要求使用 grill-with-docs 繼續。沿用前述決定及未選定事項，不從頭重問；文件保留原路徑以維持引用。從世界資料與後果契約收斂，沿用既有 NPC 決策、D20、活動時間、保存與預算；本輪涵蓋物件、環境及角色身體的外在後果（Q4）。

## 問題與既有決定

使用者在 PR #144 完成後指出：天上意志的目的，是讓 NPC 在一定範圍內自由活動；若某個環節被固定活動劇本限制而無法承接合理方法，就偏離目的。

查證基準 main `5e172d51f999f28ca17f5a207fb109d3f8c305e2`。#125、#128、活動生命週期 Grill 與 ADR 0002 已確認「天上意志提出後果內容，程式驗證並可靠執行」。這項責任分工不需重新選擇。

目前 `lib/routine-program-contract.ts` 卻要求成功 drink 包含 `contents=dirty`、wash 包含 `contents=empty` 與 `clean=yes`，並限制不同 operation 可提供的具體狀態效果。模型雖回傳程序，卻沒有合法的其他成功後果選項。這些內容限制不能一概當成身份、權限或保存安全檢查；其他固定條件仍須逐項對照成功語義，不直接刪除全部驗證。

PR #144 補新驗收杯的 dirty 能力，修復既有契約內的能力不相容，並補操作證據及 NPC 受阻指引；它沒有移除上述內容限制。先前 API／UI／SQLite 與 fixture 測試通過，不能證明整體活動自由度已符合原始目標。原正式站已通過的餐點、首次泡茶及保存重送結論保持。

## Q1：合理後果超出預列狀態時，可確認新狀態（已確認）

提問：當合理後果超出物件預先列出的狀態時，是否允許天上意志確認並保存新的狀態，例如「有茶漬」「濕潤」，而不必每次修改程式？

推薦：允許，但限於受約束的狀態描述；身份、權限、既有事實與資料大小等檢查保持。使用者回覆「好」。

本決定允許新物件狀態，不表示模型可產生程式、任意世界 patch、新效果種類，或藉狀態描述取得所有權／他人同意。具體資料表示、上限與相容方式尚未選定，不在紀錄中假稱已確認。

## Q2：後果合理性主要由天上意志判斷，接受可查證的誤判風險（已確認）

提問：是否接受「後果合理性主要由天上意志判斷」所帶來的模型誤判風險？例如杯子留下茶漬後是否適合裝水、是否需要清洗，由天上意志依情境判斷；程式檢查身份、權限、供應與保存一致性，不為每種狀態寫死答案。

推薦：接受這個取捨，並保存裁定理由與前後狀態，讓錯判能被查證、修正。使用者回覆「好」。

此決定不表示所有模型輸出都有效：回覆格式、受限效果、權限、資料上限及可機械檢查的世界一致性仍須驗證。合理性理由屬可追蹤的裁定證據，不自動成為 NPC 可知資訊；沿用操作證據與敘事／記憶隔離。未在此選定人工修正入口、自動回溯、重播或額外模型重試；既有事實不能無聲改寫。

## 沿用的約束

- NPC 自行選擇方法與後續行動；天上意志不替角色同意或強制成功。
- 已涵蓋且條件相符的日常規則重用；未涵蓋情況走有界例外裁定，不為每個階段或擲骰結果再呼叫模型。
- 身份、供應、資訊隔離、預算及派送上限保持；既有 D20 為基線，使用者提出的簡單對抗骰另於 Q7a 明示討論，不視為已實作或已確認；狀態與活動結果須可保存重讀，重送不重複執行。物件使用許可須依 Q6 及後續決定與物理可行性分開，不能將所有 owner／allowedTo 硬門檻不加區分地視為不可變約束；帳號／世界隔離與他人自主不因此放寬。
- 舊證據不能追補，已發生事實不能因新增狀態被抹除；本輪未選定舊世界遷移政策。
- 不合併、部署、修改正式世界或呼叫正式付費模型；不關閉 #104、#106。

## Q3 前提修正：框架應承接世界變化，不要求逐種實作行動

原提問讓使用者選擇「遇到引擎能力不足時，該行動未完成而世界繼續」或「暫停世界」。使用者未選 A／B，而指出預期是提供框架，讓 LLM 填入世界中發生的事，並追問為何會有框架無法處理的活動。

撤回原提問的前提：不能將目前的表達限制當成此類框架必然的限制，也不能先接受普通新活動必須等待新增專用執行器。這輪應查清通用世界變更表示能否承接活動後果；例如打碎杯子可表示原物件狀態變更，若碎片需獨立追蹤，則由通用物件建立及來源關聯承接，不因沒有「打碎杯子」函式便拒絕。這是設計方向說明，不表示現行 runtime 已具備完整表示能力。

現行 `WorldObject`／`SceneSupply` 的 kind 限 food／utensil，state 限預列轉換，materialize 限已知合法供應，日常程序又限制各 operation 的效果組合。需逐項分清安全約束與過窄的內容模型；不能只新增幾個狀態值就宣稱框架已通用化。

LLM 提供的後果仍須有可保存、供後續活動引用的結構化世界變化，不能只有成功敘述而物件未變。使用者的追問未選定任意 patch、新效果種類、技術錯誤處理或完整物件分拆／合併契約；通用操作的表示與驗收範圍須依目的具體化。Q1–Q2 仍有效。

## Q4：涵蓋物件、環境及角色身體的外在後果（已確認 A）

以打翻熱茶為例，物件可能有杯中茶減少或杯子破裂，環境可能有濕桌面或地板碎片，角色可能衣服濕了或手被燙到。使用者選 A：三類都納入，讓一次活動的外在後果能完整保存；角色怎麼想、是否原諒別人、接著做什麼，仍由 NPC 自己決定。

先用可追蹤的狀態表達，不引入生命值或完整戰鬥系統。這是本輪的承接範圍；具體狀態、身體影響及資料形式由後續設計落實，不把單一例子寫成活動必然後果。原 Q1 單獨沒有選定新通用操作集合；本輪依 Q4 的範圍設計契約，不能將現有物件專用效果清單視為永久不可擴充。

## Q5：狀態隨世界時間自然變化（已確認 A）

以熱茶冷卻、濕桌面乾燥為例，即使沒有 NPC 再操作，已形成狀態也可自然變化。使用者選 A：天上意志確認後果時，一併確認可預期的後續變化、時間與條件；程式隨世界時間執行。途中條件改變，就停止套用不再成立的變化。

此方向讓世界延續已有事件的後果，不必每回合呼叫模型詢問狀態是否已變。既有角色自主、條件驗證、操作重送與保存一致性保持；依世界時間推進，不據此新增離線常駐運行。條件變更後需要的新裁定仍受既有有界派送及預算約束，未在此批准隱藏重試。

本題處理既有事件的自然延續，不把另案的主動生成新天氣、新客人或其他無既定來源的世界事件納入。具體排程表示、時間上界、相關條件檢查與重載恢復由後續工程設計落實，不宣稱現行活動階段已完整支援這項能力。

## Q6：使用許可不使物件免於意外後果（已確認 A）

提問情境：NPC 已獲准借杯泡茶，意外把杯子打破。使用者選 A：天上意志可裁定並保存破損／損毀及來源；杯子仍屬店主，店主如何反應由自己決定。此決定明確重訪現行 owner-only destroy 對合法活動失敗分支的限制，不以偷改驗證器的方式處理。

使用者補充：「我甚至想允許一部分不道德的行為，所以這個不是所有者不能操作的概念可能也得改」。因此後續必須區分所有權、持有、使用許可與物理可行性；物主是否允許，不應未經討論就等同角色在世界中絕對做不到。

若後續選定允許未經許可拿取，其結果可以改變實際持有，但不能因此自動改成行動者所有、補出物主同意或替物主原諒。這是責任區分，不表示目前已選定所有未經許可行為的範圍、成功判定或後果。NPC 是否嘗試仍依其自主性，不能為了展示功能強制角色作惡。

帳號／世界資料隔離、物件引用與保存一致性、NPC 可知資訊、角色本人意願等仍保持。不能把遊戲內允許違反物主意願，誤解成模型可越過技術存取控制或改寫其他 NPC 內心。

## Q7 補充：簡單對抗判定與完整戰鬥系統分開

使用者回覆：「戰鬥系統其實我還沒有想到要不要加, 先用個簡單的對抗骰不行嗎」。原 Q7 的 A／B 尚未獲選擇。完整戰鬥系統不是角色動作衝突的必要前提；先討論一次對抗如何判定，不要求先選生命值、戰鬥回合或完整戰鬥規則，也不以這些尚未實作為由否定方向。

現行 `lib/d20.ts` 是主動者一次 D20 加修正，對照難度及五級結果；#7 的已確認 P1 設計明定主動者單次擲骰，對方條件影響判定，且當時將多骰對抗列為不做。這是既有產品選擇，不是引擎不可改變的能力邊界。使用者現在提出對抗骰，應明示重訪這項選擇；不能說雙方擲骰已存在，也不能直接把原本的五級門檻套用於兩骰差值而宣稱契約未變。

建議方向（尚待確認）：雙方實際形成相互衝突的行動時，例如一方搶杯、另一方護住杯子，各擲一次 D20 加情境修正後比較。角色仍自主決定如何應對，天上意志依已選方法及世界條件確認可能後果，程式負責擲骰、套用並保存結果。一次判定只處理該次衝突，不自動延伸成強制打到分出勝負；結果不能代替角色同意、原諒或改變信念。這些例子說明設計可能性，不是已確認的行動白名單。

Q7a 先確認一個決策：採雙方各擲一次 D20 加情境修正比較（推薦），或維持單方 D20 對難度、由難度表達對手阻力。平手、成功程度、反應時機與適用範圍待答案後收斂；原有同方法同條件不重擲、重送不重複擲骰、模型不決定骰面等原則保持。未在本題批准 runtime 修改、額外付費模型派送或完整戰鬥系統。

## 已查證現況及票務接點

- 物件：`lib/world-effects.ts` 已保存身份、來源、持有、所有權、狀態與生命週期，並有具體化、消耗、移動、狀態、授權、同意及損毀效果；目前仍限制 food／utensil 及預列狀態。`lib/world.ts` 的 NPC 移動會同步攜帶物件。
- 環境：`lib/perception.ts` 已有門、區域噪音及遮擋狀態。門有正常行動更新路徑；噪音、遮擋供感知使用，但本次查證未找到正常裁定候選更新路徑，不能稱完整通用環境效果。
- 角色：`lib/world.ts` 已有位置、活動、能力等資料，沒有通用身體／外在狀況集合或對應裁定效果；`mood` 與活動敘述不能代替持續身體狀態。
- 自主與認知：沿既有 `npc-memory-contract.md`、`heavenly-will-grill-2026-10-16.md` 及 ADR 0001；世界真相、可感知線索及角色主觀理解分離，裁定不任意植入記憶、修改意願或替他人同意。主動生成天氣、新客人等世界事件原已另案，不因 Q4 自動納入。
- #136／#137–#139 仍是裁定契約集中化與無副作用解析的既有工作，不是本輪擴充世界表示能力的同義票。後續 to-spec／to-tickets 需對齊這些接點，避免重複重構或互相冒稱完成；目前不開新票或改原票。
- Q6 查證：`world-effects.ts` 的 destroy 要求 actor 為 owner，因此借用者即使已獲准使用，含 destroy 的失敗分支仍遭拒；所有分支會在擲骰前驗證。一般 state=broken 則不另要求 owner，但仍需預列該狀態且通過使用權／位置／版本等前提，物件 lifecycle 保持 active；兩者並不等價。日常 v2 又不支持 destroy／condition 狀態。既有 #87／#108／#125 文件保留使用權、身份與損壞後果，但沒有明確選定合法活動引發意外損壞時的這項邊界；`free-action-effects.md` 的 owner-only destroy 是需明示重訪的現有工程契約，不能直接當成通用安全驗證而略過討論。
- Q7 前置查證：一般效果的具體化、狀態、移動、消耗及損毀，都把 owner／allowedTo 作為硬門檻；`routine-materials.ts`、`routine-rules.ts` 及 `routine-obstacles.ts` 的工具、材料、容器選擇也使用這個條件，不能只改一個 destroy 檢查就宣稱支援未經許可的行動。
- 口頭虛假陳述或保留資訊已有自由文字 say／message／persuade 的表達路徑，沒有逐句與世界真相核對的驗真器；這不等於欺騙必定成功，也不證明藏匿物件等外部效果已可執行。後續不得把說謊的表達從零開成缺少實作。
- 帳號世界 owner（登入身份、operationScope、world context、資料庫 CAS）與物件 NPC owner 是不同層次；遊戲內偷拿不放寬帳號隔離或角色可知資訊。grant／consent 所記錄的本人選擇也不能偽造為已發生。
