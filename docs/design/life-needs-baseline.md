# 自主生活需求工程基線 v1

這些是 #173/#174 的工程基線，不是使用者已確認的生理參數。驗收介面沿 #172：世界 API、真正序列化／SQLite 保存重讀、既有角色畫面。transport 與骰子可替身；不呼叫正式模型。

| 項目 | 工程值／理由 |
| --- | --- |
| 權威刻度 | 各需求 0–100，越高越需要處理；分開保存，兩位小數。有限且易查驗，不作醫學宣稱。 |
| 啟用 | 缺欄位世界在第一次成功 advance 的原世界分鐘啟用，初值飢餓20、口渴20、疲勞15、睡眠20。這是明示起點，不表示過去已吃飽或已睡足；GET 不初始化或回填。新世界沿相同起點。 |
| 清醒時間基線 | 每世界小時飢餓+3、口渴+6、體力疲勞+1、睡眠需求+4。15分鐘可查驗、數小時可跨區間；只算已提交世界時間。 |
| 感受區間 | <40 無明顯訊號，40–<65 輕微，65–<85 明顯，85–100 強烈；基線初值至少經數小時才升級，避免初次啟用把既有短活動頻繁打斷。只投影文字，不投影數值、係數或他人需求。 |
| 重新評估 | 清醒原活動遇到任一需求進入高於已評估區間時，在下一個正常 slot 合併為一次決策；本人可續做。正常決策成功候選把四項當前區間記為已評估。降低區間同時降低已評估記號，之後再升級可重觸發。沒有逐 tick 記憶、懲罰或新增模型。 |
| 有限追溯 | 最多32次時間／效果變化，省略筆數明示；不宣稱永久身體史。 |
| 相容與回退 | JSON optional needs，舊資料、舊活動及舊規則保留；回退版本讀寫可能不認識新欄位，需保留完整世界備份後回退，不能把丟欄位當遷移。 |

活動後果與睡眠在後續票明列確認規則；舊規則缺少新需求效果時保持未確認，不能由讀取推測恢復。

## #174 活動後果基線（實作前工程定稿）

- `ingest` 是原有物件消耗的有界擴充：同一步真正消耗本人持有的可攝取物件，並確認該完整物件的飢餓／口渴緩解各0–60。至少一項大於0；沒有隱含補貨。部分攝取必須先沿既有 `separate` 分出具體份量，`ingest` 只消耗該部分。這不是熱量系統或依名稱猜營養。
- `bodyActivity` v1 是本次活動裁定確認的時間後果，kind=`rest|exertion|sleep`，rest 的額外疲勞變化 -20..0/時、額外睡眠需求變化必須0；exertion 額外疲勞0..20/時、額外睡眠需求必須0；sleep 額外疲勞-20..0/時、額外睡眠需求-20..<-4/時，與清醒基線相加後必須實際降低睡眠需求。各kind均在候選驗證時檢查，清醒休息不能冒充睡眠恢復。只算本次真正發生的活動分鐘；未執行提案、未開始活動或未來時段沒有恢復。睡眠狀態由#177承接。
- 既有內建清醒休息的新開始採程式明列規則：疲勞額外-9/時（合計-8/時），睡眠額外0（仍+4/時）；一般明示工作額外疲勞+3/時（合計+4/時）。不從文字判斷已睡著。舊活動及舊日常規則沒有profile時保持沒有活動恢復，不冒稱已由模型確認；新一般方法可沿原裁定承接profile。
- 對照用fixture：一份已形成餐點hungerRelief=30、一杯已形成茶thirstRelief=25；這些是裁定fixture值，產品不以food/tea名稱自動套固定恢復。

- 時間與profile先合成有限積分，再一次截斷至0–100；首段新開始保留尚未截斷的fatigue/sleep基底，避免原值100時先截斷清醒增量再減恢復造成額外恢復。切換活動只套尚未由前活動覆蓋的實際分鐘，不雙算同段時間。

## #181 舊方法的明示身體後果再確認

以下是保留舊資料的工程承接政策，不是使用者已確認的數值參數：

- 舊規則、舊活動與普通 `consume` 保留原義；GET不自動升級、不新增模型、不依名稱補上恢復。觀察者日常規則面板明示此缺口。沒有選擇重新確認時，舊方法仍可能真正吃喝但沒有新契約的需求緩解。
- NPC 可在同次正常 `propose` 明示 `reconfirmBodyConsequences=true`，語義是「想重新確認這個方法對自己身體的實際影響」。缺省false；不把scope/版本或身體數值送給角色。只有已有可執行方法、且既有候選未含明示 `ingest`／`bodyActivity` 時，才略過該次免費舊綁定，沿本來的普通裁定slot確認；沒有獨立呼叫。
- accepted重新確認必須保存含明示攝取或時間後果的獨立v3範圍；舊規則不改寫。後續同方法與適用條件優先綁定新身體後果範圍，重複true亦不增加裁定。身體效果的數值與物件／時間仍受原驗證。
- denied／unsupported的重新確認保留有界receipt：actor、方法、原範圍及相關既有物件版本／份量、供應餘量等構成精確signature（最多8192字），最多32筆、超過最舊淘汰並計缺口。同一方法與相關事實不變時，再選重新確認會取得「尚未能確認、這次未開始」的可知回饋，零裁定；不因每tick需求數值變化重問。角色仍可改方法、在相關條件變化後再試，或選擇舊原義。receipt只供引擎與觀察者，與整輪共同保存，不是NPC記憶或偏好。
- 淘汰後可能再次確認，接受有限追溯取捨，不宣稱永遠記住每次未確認結果；已確認範圍本身仍沿既有規則容量保存。
