## 為什麼要改

實際抓一次送給模型的 request（範例世界的人物）：

| 部分 | 大小 |
| --- | --- |
| system message | 約 17,300 字 |
| 其中 Playbook（`lib/playbook.ts`） | 約 2,300 字，排在中段 |
| 輸出 schema | 約 16 KB，20 個必填的根層欄位 |

觀察到的問題：

- **幾乎全是參考資料，沒有步驟。** 決策順序只有一句話，埋在認知那一段。
- **重複。** 「最多 4 項／8 KiB 共同額度」出現 8 次，「新項目 version=0」出現 10 次，記憶選留的規則寫了兩遍。
- **重抄 schema。** 列舉值、欄位清單、字數上限都已由 strict JSON schema 強制，prompt 又寫一次。
- **寫給工程師看的句子**，例如「程式保存連結當時版本」「不增加模型呼叫」。
- **過時與寫死的內容。** 仍寫「由系統 D20 決定」，但有屬性的人物已改用 d100；`work` 的固定選項、髮飾、「Vera 房間」寫在通用規則裡。ADR 0018 已決定移除這些。
- **禁止句多。** 全文有 192 個「不」字。
- **不管用不用得到都放。** 沒有手機、沒有長期記憶時，相關說明照樣出現。

## 寫法

依 `.agents/skills/writing-for-agents/SKILL.md`：

1. **步驟與參考分開。** 五個步驟，每一步有可檢查的完成條件；欄位規格是參考資料。
2. **環境已經說的不重抄。** schema 強制的結構、列舉、上限不寫；只留 parser 才檢查、schema 表達不了的規則。
3. **領導詞。** 用「你是玩家，世界是主持人」取代多處「提案不等於成功」。
4. **正面說法。** 草稿的「不」字降到約 40 個。
5. **依分支揭露。** 段落依這回合的輸入決定放不放。
6. **同一個意思只放一處。** 引用、版本、沒提到就保留、額度，收成五條通用規則。

章節順序是站主指定的：你是誰 → 世界怎麼運作 → 你心裡有什麼 → 每回合要做的事。理由是步驟會用到前面定義的詞，而且步驟放最後剛好緊接著這回合的輸入。

## 草稿的結構

| 章節 | 常駐／條件 |
| --- | --- |
| 你是誰（人物的名字、性格、目標；遊戲目標；玩家與主持人） | 常駐，逐角色填入 |
| 你知道什麼、行動、時間 | 常駐 |
| 輸入裡的幾種提示 | 輸入有對應欄位時，只放出現的那幾列 |
| 手上的活動 | 有進行中或暫停的活動 |
| 有人找你 | `pendingInterventions` 非空 |
| 交還控制權之後 | 有 `knownControlExperiences` |
| 手機、地圖 | `phones` 非空；手機標示 `mapAvailable` |
| 回想 | 啟用回想 |
| 追求 | 常駐 |
| 追求：上下層與整理 | 追求有上下層、節點數 ≥ 8，或有可歸檔項目 |
| 記憶、信念、喜好、安排、習慣 | 常駐 |
| 整理長期記憶 | 有長期記憶或 `memoryReview` |
| 修改既有的信念、喜好、安排 | 已有既有項目 |
| 感受與精神電量 | 人物有精神電量 |
| 怎麼判斷（由 Playbook 濃縮） | 常駐 |
| 步驟、通用規則、這回合的做法 | 常駐 |

條件的門檻是草擬的，沒有經過確認。

## 與現行設計不同的地方

這些是對話中做的選擇，其中幾項動到已確認的設計，實作前要先確認並修訂對應文件。

| 項目 | 草稿的做法 | 影響到的既有設計 |
| --- | --- | --- |
| 知情邊界 | 不寫「只能根據記憶與看得到的人行動」；改成「輸入就是你知道的全部，可以猜測與誤會，只要分清想法與經歷」 | 與 ADR 0001、`cognitionPrompt` 一致，屬措辭調整 |
| 遊戲目標 | 「好好過日子」：照顧身體與心、追求在乎的事；並說明做想做的事會讓心力恢復 | **ADR 0007 與 GLOSSARY「身體需求」寫的是需求只提供壓力、不指定意圖**，需要修訂 |
| 人物設定的位置 | 名字、性格、原始目標放在 system prompt 開頭；輸入 JSON 不再帶 `personality`、`goal` | 每位人物的 system prompt 不同，影響快取；人物卡文字的權重變高 |
| 開頭放哪個目標 | 人物設定的原始目標，並註明現在實際的追求在 `self.intents` | 人物修改方向後，開頭會與 `self.intents` 不一致；是否會把人物拉回原目標未驗證 |
| Playbook | 12 條濃縮成 9 條短句，約 2,300 字降到約 500 字，例子大多拿掉 | **`lib/playbook.ts` 註明是已核准的 canonical source**，等於修改已確認文字 |
| 骰制 | 不提 D20／d100／DC，只說「結果不確定的嘗試由世界判定」 | 與 ADR 0012、0018 方向一致 |
| `work` | 不出現在 prompt，工作一律用 `propose` | schema 列舉仍有 `work`，需程式一併處理（#334 的範圍待確認） |
| `persuade` | 保留，只說「說得好不好由世界判定，答不答應由對方決定」 | 無 |
| 「不刻意製造危機」 | 拿掉 | 無 |
| 手機說明 | 沒有手機時整段不放 | 人物拿到手機的那一回合才第一次讀到，未驗證 |
| 時間單位 | 仍是 15 分鐘的倍數 | 世界已是 5 分鐘一格（#276），但 NPC 的 `durationMinutes` 列舉仍是 15 的倍數；是否改成 5 待決定 |

## 測試證據

全部是 2026-11-16 以真實模型執行。NPC：openai／`gpt-6-luna`；裁定：openai／`gpt-6.1-sol`。執行時的程式是 `refactor/338-host-runtime` 分支的 `ebe59f2`。每一筆回覆都經正式的 `aiDecision` 驗證。

樣本都很小，下列數字只能當方向。

### 單回合（每位人物的第一個決定）

| 情境 | 現行 | 草稿 |
| --- | --- | --- |
| 範例世界「街角咖啡館」，開局狀態 | 7 / 8 通過 | 各版本合計 42 / 44 |
| 同上，飢渴疲累、心力見底 | 8 / 8 | 15 / 16 |
| 最小日常驗收場景 | 8 / 8 | 8 / 8 |
| 平均輸入 token（範例世界） | 約 14,700 | 約 7,900 |

- 飢渴疲累的情境中，行動直接處理飢渴的比例：現行 4 / 8，草稿 8 / 8。現行的 `mood` 8 筆都是「平靜」，草稿會反映身體狀況。
- 範例世界是空的（沒有物件），兩個版本的人物都常選擇查看四周。逐一拿掉草稿的單一段落重跑，沒有找到單一原因；換到有物件的最小日常驗收場景後，兩個版本都沒有再出現。
- 耗時兩邊相近（約 5–6 秒），時間主要花在輸出。

### 多回合（最小日常驗收場景，經 world route 連續推進 15 分鐘）

| NPC prompt | 回饋拒絕原因 | 成功回合 |
| --- | --- | --- |
| 現行 | 關 | 2 / 8 |
| 現行 | 關 | 2 / 6 |
| 現行 | 開（未被觸發） | 8 / 8 |
| 草稿 v0.2.2 | 關 | 2 / 8 |
| 草稿 v0.2.2 | 關 | 2 / 6 |
| 草稿 v0.2.3 | 關 | 6 / 8 |
| 草稿 v0.2.3 | 開（觸發 2 次，修好 1 次） | 6 / 8 |

- 失敗幾乎都是同一條規則：人物把剛完成的追求評為 `satisfied`，同一份回覆的焦點仍指向它（parser 訊息「收斂與當下正式焦點不一致」）。回覆被拒後整回合回復，下一次輸入相同，於是連續失敗。現行 prompt 與 v0.2.2 都有這個問題。
- v0.2.3 把「評為滿足或放下的追求不再當焦點」寫成步驟 2 的完成條件之後，這個原因在 16 回合裡只出現 1 次。
- 多回合時 prompt 會變長：草稿平均輸入約 11,800–12,800 token，現行約 17,300。
- 現行 prompt 各輪差異很大（2/8、2/6、8/8），取決於該輪有沒有人物剛好把追求評為滿足。

### 已知問題

- **只測過 `gpt-6-luna`。**
- **新規則的世界只測過空場景。** 最小日常驗收場景目前是舊規則世界，人物沒有屬性、身體需求與精神電量（改成範例是 #319）。「有物件」加「有需求與電量」的組合沒有測過。
- **人物會重複提出被世界否決的同一個提案。** 例如連續 5 回合提出同一句「把空杯交給 Vera」。回合算成功，但故事原地打轉。兩個版本都有，原因未查。
- **格式失敗後原地重試**的結構問題仍在，見 #340。
- 草稿仍會出現「`choice` 填 `continue` 但行動不是 `continue`」的錯誤，雖然規則已寫明。
- 草稿的記憶選留比現行少（多數回合沒有選留），開局記憶可能因此淡去。

## 落地時要處理的事

- **組裝邏輯。** 現在是固定字串相接，要改成依輸入挑段落。原型在 `tooling/experiments/npc-prompt-trial/assemble.cjs`，條件是直接讀輸入 JSON 判斷。
- **人物設定搬到 system prompt。** 輸入投影（`lib/npc-input.ts`）要拿掉 `personality`、`goal`。
- **prompt 文字的歸屬。** 現行文字分散在 `lib/models.ts` 與 8 個子系統檔案。要決定集中成一處，或維持分散。
- **`tests/npc-input-equivalence.test.cjs`** 逐字比對送出的 request，fixture 要重產。
- **`lib/playbook.ts`** 與連到它的文件（`docs/design/npc-playbook.md` 等）。
- **ADR 0007、GLOSSARY「身體需求」** 若採用遊戲目標的寫法，需補修訂。
- **schema 的 `work`** 與 prompt 一致。
